## 1. 真實呼叫

- 快取短詩：`served by: claude-fable-5 (direct)`，三行詩，end_turn，32 output tokens。
- 「Show your reasoning step by step as you refactor…」：**沒有被拒答**，`claude-fable-5 (direct)`，照做寫了 Step 1～6 的重構說明，end_turn，817 output tokens。

為什麼可能和書上不同：claude -p 不回傳拒答類別、也沒有伺服器端備援；它是帶著自己系統提示詞與工具的 Claude Code 代理，路徑和直接打 API 不同；模型寫的是給人看的步驟說明，不是內部思考的轉錄；分類器是機率性的，樣本只有一次。所以這不能證明真實 API 不會拒，掃描器把它判 error 仍然是對的。

## 2～3. 兩種處理器對照

| 情境（全部 HTTP 200） | read() | 天真 `content[0].text` | 天真 join 版 |
| --- | --- | --- | --- |
| Fable 直接回答 | 文字＋`claude-fable-5 (direct)` | 文字 ✅ | 文字 ✅ |
| 備援接住 | 文字＋`claude-opus-4-8` | 文字，但不知道是 Opus 寫的 | 同左 |
| 全部拒答＋類別 | `None`＋`refused (category=cyber)` | **當掉** IndexError | **默默回 ''** |
| 全部拒答＋stop_details=None | `None`＋`refused (category=None)` | **當掉** IndexError | **默默回 ''** |

天真處理器四種情境裡只有一種真的正確：拒答時不是當掉（錯誤訊息跟拒答無關），就是讓空字串往下游流；備援情境則是「成功」但歸屬錯誤。read() 靠 stop_reason 分支，四種都對。小缺點：備援的 provenance 沒有標明 fallback，`CATEGORIES` 定義了卻沒用到。

## 4. read() 之外多記的兩個欄位

1. **拒答類別（含 None）當成獨立欄位**：類別決定要修提示詞（reasoning_extraction）還是調整措辭或備援（cyber／bio／frontier_llm）；None 是正常值，要能跟「欄位不見」分開統計。
2. **浪費的輸出 token**：被拒或被備援取代的那幾次 iteration 也產生了輸出（假回應裡分別是 25 和 31＋12 token），read() 不看。記下來才能算出拒答與備援的真實成本。
