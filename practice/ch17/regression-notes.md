# 回歸測試筆記

## 逐字比對失敗、性質斷言通過（ch17/test-results.txt）

同一個提示詞「用 JSON 回答：{"lang": 程式語言名稱, "reason": 一句理由}，題目：寫命令列小工具首選哪種語言？」送了 2 次：

| | 原始輸出 |
| --- | --- |
| 第 1 次（78 字元） | `{"lang": "Go", "reason": "編譯成單一執行檔、跨平台部署簡單，且有豐富的 CLI 函式庫（如 cobra），非常適合命令列工具。"}` |
| 第 2 次（61 字元） | `{"lang": "Go", "reason": "編譯成單一執行檔、跨平台部署容易，且標準庫對 CLI 開發支援完善"}` |

- **逐字比對：FAIL**。兩次的 reason 用字不同（「簡單」對「容易」、一次提到 cobra、一次提到標準庫），長度 78 對 61。
- **性質斷言：兩次都 PASS**：都能直接 `json.loads`（沒有包 ``` 圍欄）、都有 lang 與 reason、reason 都短於 120 字元。而且兩次的 lang 都是 Go，真正重要的答案是一致的。

如果這是 CI，標準答案測試每一次重跑都可能變紅，但程式的實際契約（下游能解析、欄位齊全、長度合理）完全沒被打破。這種測試只會讓人學會忽略紅燈。

(b) 三個提示詞的 `c._score` 都是 100%：

| id | effort | expect | 輸出 |
| --- | --- | --- | --- |
| classify-low | low | contains network、max_len 12 | `network`（7 字元） |
| explain-high | high | contains 相容、min_len 40、max_len 400 | 162 字元，解釋新舊版本同時運行、先做只新增欄位的相容變更 |
| format-default | 不送（API 預設 high） | exact `apple, banana, cherry` | `apple, banana, cherry` |

注意 format-default 用的是 `exact`，它之所以通過，是因為答案只有一種寫法。這是例外：只有在答案空間真的只有一個值時，逐字比對才合理。

## 預設門檻對 4% → 11% 的結論（ch17/threshold.txt）

直接複製 `run_canary()` 第 108～120 行的比較邏輯，模擬 100 個提示詞：

- 拒答率差 0.11 − 0.04 ＝ **0.07**（拒答率變成 2.75 倍）。
- 預設 `refusal_max=0.2` 的條件是「差 > 0.2」，**不會告警**。平均分數 89%（拒答算 0 分）也高於 0.6，所以分數那條也不會響。
- 能抓到這次漂移的最大 refusal_max 是 **0.069**（以 0.001 為間隔掃描）。因為條件是嚴格大於，0.07 剛好抓不到。
- 預設 0.2 下，基準 4% 時要到 **25 個拒答（25%）**才會告警，也就是基準的 6.2 倍。等它響的時候，四分之一的流量已經被拒了。

**結論**：預設門檻對這次的漂移完全是瞎的。0.2 是「絕對差 20 個百分點」，對基準只有幾個百分點的系統來說太寬鬆；拒答率從 4% 跳到 11%，在任何正式環境都算嚴重事件。

**建議門檻**：改成第 16 章那種「絕對差或倍數」的雙條件，並要求最少樣本數：
- 絕對差 > **0.03**（3 個百分點），**或**倍數 ≥ **2 倍**；
- 且本次至少 50 個提示詞，避免樣本太少時一兩個拒答就讓比率暴衝。

依據：基準 4%、100 個提示詞時，拒答數的標準差約是 √(100 × 0.04 × 0.96) ≈ 1.96，11 個比預期的 4 個多了約 3.6 個標準差，不太可能是隨機波動。3 個百分點的門檻大約對應 1.5 個標準差，同時用 2 倍條件，基準很低的時候也抓得到。

## 替不同 effort 各加一條斷言

- **低 effort（low）**：加「**已知答案的正確性**」斷言。低 effort 的風險是想得太少、太快下結論，而不是格式錯。像 classify-low 這種有標準答案的分類題，除了格式（一個單字、max_len），要再斷言「答案必須等於 network」，也就是一批題目的**準確率不得低於基準**。光看格式，低 effort 答錯也會滿分。
- **高 effort（high）**：加「**長度上限**」斷言（例如 explain-high 的 max_len 400，或「不超過 3 句」）。高 effort 的風險是寫太多、做太多（第 6 章的 no-gold-plating），輸出變長也會讓成本跟著漲（第 10 章）。這次 162 字元離上限還很遠；如果哪天模型更新後變成 600 字元，正確性沒變，這條斷言會先響。

這兩條剛好對應兩種 effort 最常見的退化方向：低 effort 會變「不準」，高 effort 會變「囉嗦」。
