## prepare_history(messages, source_model, target_model)

- 先對輸入做深拷貝，傳入的物件不會被修改。
- **同模型**：直接回傳深拷貝，`json.dumps` 逐位元組相同，空 thinking 與 redacted_thinking 都保留。
- **跨模型**：只移除 assistant 訊息裡 type 為 thinking／redacted_thinking 的區塊；user 訊息和字串形式的 content 不碰。
- 某則 assistant 因此變空時，補一個說明 text 區塊。註解寫明原因：整則刪掉會讓兩個 user 相鄰、破壞交替結構；留空陣列又不被 API 接受。
- 不是 list 就拋 TypeError。

## 檢查結果

1. 同模型逐位元組相同＋是深拷貝 ✅
2. 跨模型沒有任何思考區塊 ✅
3. 兩次呼叫後原物件未被改 ✅
4. tool_use／tool_result 保留，toolu_01 對得上 ✅
5. 只剩 redacted_thinking 的那則變成說明 text，訊息數 8、交替結構不變 ✅
6. 非思考區塊逐字相同 ✅
7. 邊界：空歷史、非 list ✅
8. linter（model=claude-opus-4-8）：處理前 3 條 `messages` warn → 處理後 **clean** ✅

錯誤示範：`well_meaning_cleanup` 在同模型時刪掉空 thinking，逐位元組比對變成 False（914 → 849 字元）。

另外發現：linter 對每則帶思考區塊的 assistant 訊息各報一次 warn，所以出現 3 條一樣的警告。

## 兩條規則為什麼方向相反

思考區塊只對產生它的模型有意義。同模型時，它帶著簽章或加密內容，是要原樣交還的狀態：改一個位元組就可能驗證失敗、快取失效、fallback credit 兌換失敗，連空的 thinking 也是狀態的一部分。換模型時，新模型看不懂也驗證不了別人的思考區塊，快取本來也要重建，所以一定要拿掉；但 text、tool_use、tool_result 是對話的事實，要原樣保留，tool id 也要成對。
