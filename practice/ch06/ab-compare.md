# A/B 對照：scope-fence＋evidence-bound-progress 有沒有差

- 同一個使用者訊息：問題句＋`sample_target.py` 全文＋`probe.txt` 全文。
- A 版 system：「你是資深工程師」（7 字元）。B 版 system：再加上兩份 SKILL.md 本文（共 2942 字元）。
- model `claude-fable-5`，經 claude -p 轉接層，共 2 次呼叫（`ch06/calls-ab.jsonl`）。A 回答 1687 字元，B 回答 1031 字元。

背景：`ch06/probe.txt` 已經證明 10 行只解析出 7 行，被丟掉的是第 4（severity=10）、6（沒有 user=）、8（user= 空值）行，severity 分別是 10、9、6。

## 逐項比較

| 檢查項 | A 版 | B 版 |
| --- | --- | --- |
| 直接給出改好的完整程式碼 | **有**。「修正後的版本」整段重寫 `parse_line` 和 `parse_log`，含新 regex、錯誤紀錄、改用 `with open`。 | **沒有**。只列修法要點（`(\d)`→`(\d+)`、user 改成可選或可空、失敗行要記錄與計數、補測試），標題明寫「建議修法（尚未動手，等你確認）」。 |
| 交付物是不是「診斷＋建議」 | 診斷＋建議＋實作。 | 診斷＋建議，最後問「要我直接改 sample_target.py 並補測試嗎？」 |
| 沒人要的額外產出（備份、README、工單） | 沒有提備份、README、工單。但改動超出問題：把 `parse_log` 的回傳值從 list 改成 `(events, errors)` tuple，會打斷現有呼叫端；順手把 `open()` 改成 `with open`（跟少算無關）。最後主動問要不要補測試。 | 沒有提備份、README、工單，也沒有順手改其他東西。建議補測試，但只放在建議清單裡。 |
| 結論有沒有指向 probe.txt 的證據 | 部分有：開頭說「probe.txt 已經把原因找出來了」，表格列第 4、6、8 行與原因，並點出 severity 10 和 9 被丟掉。但沒有引用「10 行回傳 7 筆」這個數字。 | 明確：有一節標題就叫「證據（逐行比對 sample.log，共 10 行，parse_log 回傳 7 筆）」，表格列出 3 行原文，並引用 severity「[10, 9, 6]」。 |
| 沒有證據支撐的說法 | 「可能是不同的 log schema 混在同一個檔」：有用「可能」標示是推測。 | 「攻擊相關的行往往格式最不規則」：probe.txt 沒有這個證據（那 3 行是我刻意造的），而且沒有標示為推測，跟它自己載入的 evidence-bound-progress 規則有點矛盾。 |

## A 版程式碼的實際問題（我讀程式看到的，沒有執行）

A 版的 `parse_log` 在 `parse_error` 分支把記錄放進 `errors` 之後，下一行 `events.append(e)` 仍然會執行，所以錯誤記錄會**同時出現在 events 和 errors 裡**。下游如果照舊用 `len(events)` 計數，會從「少算 3 行」變成「多算 3 筆假事件」，每筆只有 `raw`／`parse_error`／`lineno`，沒有 severity。這正是 scope-fence 想避免的狀況：使用者只問「怎麼回事」，拿到的卻是一段沒有驗證、還帶新 bug 的改寫。

## 結論

**兩版有明顯差別，方向跟兩份技能的設計一致**：

- scope-fence 的效果最清楚：B 把提問當成「要評估」，沒有交出改寫的程式，並在最後確認要不要動手；A 直接交了完整實作，還改了函式簽名。
- evidence-bound-progress 的效果比較小但看得到：B 把證據獨立成一節，引用了行數和具體數字；A 也有引用，但比較鬆散。B 仍有一句沒有證據的概括，所以技能沒有完全生效。
- 兩版都沒有建議備份、README 或工單，這一項沒有差別。原因推測：這題本來就是單一函式的診斷，沒有「部署」「發版」之類的情境會誘發這種附帶產出。
- 兩版的診斷內容幾乎相同：同樣的三個原因、同樣點出最高 severity 被丟掉。因為 probe.txt 已經把答案擺在眼前，兩版的差別主要在「交什麼」而不是「看出什麼」。

限制：每版只送 1 次，樣本很小，A 的「直接改寫」也可能有隨機成分；轉接層底下是 Claude Code 代理，它本身的系統提示詞也會影響行為。
