## 切換建議

兩個工作**可以**切到 Fable 5，四筆全部滿分，output_tokens 幾乎相同。但 Fable 每 token 單價是 Opus 4.8 的兩倍（$10／$50 對 $5／$25），這兩個又是低判斷力的例行工作，切過去品質不會提升；照一句話測試，分類工作反而該往下切到 Haiku。正式切換前要用一批真實輸入看通過率，而不是只跑一次。

## 性質通過但字面不同，為什麼不算回歸

兩份摘要的分點方式和用詞都不同，但下游依賴的是性質（三點、長度、標籤能被程式比對），這些都一樣。模型本來就不保證逐字相同，用字面比對當回歸標準，每次升級都會誤報，最後大家就會忽略這個測試。回歸應該定義成「下游契約被打破」。缺口：我的摘要檢查只看格式，沒檢查關鍵事實（DB_POOL_SIZE、0.2%）；這次是我看原文才確認兩邊都有。

## 轉接層的影響

- max_tokens（300）被忽略：真實 API 會截斷囉嗦的輸出並讓檢查失敗，轉接層下不會，所以可能高估真實環境的通過率。這次兩邊都只用約 160 token，沒有影響。
- fallbacks 被忽略：真實環境下，Fable 的回答可能其實是 Opus 備援寫的；轉接層下四筆一定是各自的模型，比對比較乾淨，但測不到「切過去有多少比例會被分類器擋下」。資安類工作切換前必須用真的 API 測。
- 兩個模型都跑在同一個 Claude Code 外殼下，比較公平，但 token 數與延遲的絕對值不等於直接打 API。
