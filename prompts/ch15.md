# ch15｜備援靜默失效的地方

## 這章在講什麼

- 伺服器端備援不是哪裡都有：批次 API、透過雲端平台託管的端點、工具內部的巢狀子呼叫，都不會自動繼承備援。
- 在這些盲區，拒答會原樣回到你手上，必須由客戶端補一輪：把被拒答的項目挑出來，送到備援模型做第二輪。
- 更要分清楚錯誤類型：只有「拒答」該轉備援；429 限流、平台過載、網路逾時不會觸發備援，該做的是退避重試同一個模型。混在一起，容錯就失效。

## 作者做過的實驗／例子

- 批次 API 裡被拒答的項目直接回傳拒答結果，需要客戶端第二輪補救。
- 把 429 或逾時當成拒答丟去備援，或把拒答當成暫時錯誤一直重試，都會讓容錯架構失靈。

## 演練

### 練習 1：批次結果分流器，並真的跑一次第二輪補救

**目的**：把「哪種錯誤走哪條路」寫成程式，並用轉接層對被拒答的項目真的跑第二輪。
**送給練習視窗的提示詞**：

```text
1. 在 ch15/batch_results.jsonl 自造 8 筆批次結果（每行一筆，有 custom_id、request（含 model 與一個短 user 提示詞）、result）：3 筆成功、2 筆 stop_reason="refusal"（類別 cyber 與 reasoning_extraction）、1 筆 HTTP 429、1 筆 overloaded_error、1 筆 timeout。被拒答的兩筆提示詞請用無害但帶資安詞彙的內容（例如「說明 SQL injection 的防禦方式」）。
2. 寫 ch15/second_pass.py：
   - classify(result)：回傳 "done"、"fallback"（只有拒答）、"retry_same_model"（429、overloaded、timeout），其他未知錯誤回 "manual"；
   - 底部 assert 每一筆的分類；
   - 對分類為 fallback 的項目，照 B 樣板 install 轉接層後，用 claude_cli_client.Anthropic().messages.create 以 model="claude-opus-4-8" 真的送出原本的提示詞（2 次呼叫），把結果寫進 ch15/second_pass_out.jsonl（保留 custom_id 與「由誰服務」）；
   - retry_same_model 的項目只印出「會以指數退避重試，第 1/2/3 次等待幾秒」，不要真的送。
   執行並存輸出到 ch15/second-pass.txt。
3. ch15/fallback-gaps.md：表格列出書中提到的盲區（批次 API、雲端託管端點、巢狀子呼叫），各自的補救做法；並說明如果把 429 當成拒答丟去備援，會造成哪兩個問題。
```

**觀察重點**：

- 429／overloaded／timeout 是否都沒有被送去備援？
- 第二輪是否只對 2 筆拒答真的呼叫、結果有 custom_id 可追？
- 盲區表是否完整、補救做法具體？

## 教練解說要點

- 備援只對「拒答」有效，而且只在支援的介面上自動發生。
- 盲區要客戶端補一輪；補之前先分類錯誤，限流與過載是退避重試，不是換模型。
- 第二輪的結果要保留「由誰服務」，否則之後的成本與品質分析會失真。
