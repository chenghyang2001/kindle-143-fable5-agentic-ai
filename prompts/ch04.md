# ch04｜昂貴規劃，廉價建置：安全專案組合

## 這章在講什麼

- 一個模式套十個專案：prep（便宜模型把原始資料整理成工作封包）→ plan_or_audit（Fable 5 花在判斷最密集的規劃或稽核）→ execute（便宜模型照計畫做）→ verify（全新上下文的審查者只看計畫與產出物）。
- 這個共用迴圈就是 `job_packet/packet.py`；十個專案（威脅建模、MCP 稽核、成本儀表板、重構舊程式、政策轉程式、GRC、上線前稽核、SOC 儀表板、遷移、紅隊箱）都附通用範例資料，不需要你的真實程式碼。
- 「一句話測試」：一個任務如果沒有分支、沒有判斷，就該交給最便宜、做得到的那個模型——甚至交給純 Python。
- 資安專案很容易誤觸 cyber 分類器，所以 plan_or_audit 會回傳「是否被轉到備援」的類別，建置前先確認。

## 作者做過的實驗／例子

- 沒有具體停止條件的代理常陷入反覆探索，一個 session 就可能把整個專案的 token 預算吃光。
- 威脅建模、紅隊演練這類任務的安全詞彙最容易觸發 cyber 拒答，要先接好備援。
- 成本儀表板專案的 prep 刻意不用模型：加總算術交給 Python 就好。

## 演練

> 說明：兩個練習都用 `run_with_cli.py` 原封不動跑專案腳本，並用 `K143_CLI_LOG` 把每次呼叫記下來，之後交給 fable_scanner monitor 分析。

### 練習 1：跑一遍成本儀表板，看誰花了錢

**目的**：看到 prep／plan／execute 各由哪個模型負責，並用呼叫紀錄驗證。
**送給練習視窗的提示詞**：

```text
請讀 fable5/job_packet/packet.py 與 fable5/projects/03_cost_dashboard/cost_dashboard.py、sample_usage_log.csv。
1. 執行（約 2 次模型呼叫，可能要 1 分鐘）：K143_CLI_LOG=ch04/calls-03.jsonl PYTHONUTF8=1 python run_with_cli.py fable5/projects/03_cost_dashboard/cost_dashboard.py，把完整輸出存 ch04/run-03.txt。
2. 執行 cd fable5 && PYTHONUTF8=1 python -m fable_scanner monitor ../ch04/calls-03.jsonl，輸出附在 ch04/pipeline-03.md。
3. ch04/pipeline-03.md：畫一張文字流程圖（prep → plan_or_audit → execute → verify），標出這個專案實際走了哪幾段、每段用哪個模型與 effort（從程式與 log 對照，不要猜）；週摘要的金額是 Python 算的還是模型算的；模型提出的「錯路由」清單裡，挑兩項用 sample_usage_log.csv 的實際數字驗算它說的金額對不對。
4. 用一句話測試檢查：這個專案自己的四段，哪一段其實可以降級（例如 execute 只是排版），理由是什麼。
```

**觀察重點**：

- 是否從 log 與程式交叉確認模型，而不是憑印象？
- 模型給的節省金額，抽驗後對不對？算錯也要照實說。
- 是否理解「算術交給 Python、判斷交給模型」的分工？

### 練習 2：MCP 連接器稽核：規則先行，模型補判斷

**目的**：體會一句話測試——能用規則判的先用程式判，模型只處理需要判斷的部分。
**送給練習視窗的提示詞**：

```text
請讀 fable5/projects/02_mcp_audit/mcp_audit.py 與 sample_mcp_servers.json。
1. 先不用模型：寫 ch04/mcp_rules.py，用純 Python 對 sample_mcp_servers.json 套四條規則：scope 含 admin 或萬用字元（*）、auth 為 none、超過 90 天沒用、金鑰放在環境變數（env_var_key）。每個連接器印出命中的規則與 0～4 分，排序後存 ch04/mcp-rules.txt。
2. 再跑真的專案（3 次模型呼叫，約 1～2 分鐘）：K143_CLI_LOG=ch04/calls-02.jsonl PYTHONUTF8=1 python run_with_cli.py fable5/projects/02_mcp_audit/mcp_audit.py，輸出存 ch04/run-02.txt。
3. ch04/mcp-compare.md：表格對照每個連接器「規則分數」與「模型稽核的排名與建議」；列出模型抓到、但四條規則抓不到的判斷（例如功能重疊、需要逐工具政策而不只是縮 scope）；也列出規則就足夠、不需要高階模型的部分。最後一句話結論：這個專案的 prep 是否該改成你的 mcp_rules.py。
```

**觀察重點**：

- 純 Python 規則的分數是否正確（old-jira-connector、aws 應該很高）？
- 模型額外貢獻的是不是真正需要判斷的東西，而不是重複規則？
- 是否只跑了 3 次呼叫？

## 教練解說要點

- 「昂貴規劃、廉價建置」不是口號，是每個專案的固定四段；高階模型只出現在判斷最密的那一段。
- 一句話測試：沒有分支、沒有判斷的，交給便宜模型或程式。
- 呼叫紀錄（log）讓成本可以被追查，不用相信模型自己的說法。
- 資安題目容易誤觸拒答；本次用轉接層看不到備援，但真實部署一定要先接好。
