# ch08｜錯誤處理器看不見的拒答

## 這章在講什麼

- Fable 5 的拒答不是例外，也不是 4xx／5xx：它是 HTTP 200，stop_reason 是 "refusal"，content 是空陣列。只檢查狀態碼的錯誤處理完全看不到它。
- 正確的讀法：先看 stop_reason，再決定要不要讀 content；並從 usage.iterations 判斷這一輪是 Fable 直接回答，還是備援模型接住的。
- 拒答有類別（cyber、bio、frontier_llm、reasoning_extraction），要記錄下來，之後才能分析。
- 如果拒答發生在串流中段，已經吐出的 token 還是會計費，要記錄成浪費的輸出 token。

## 作者做過的實驗／例子

- 傳統只看狀態碼的監控儀表板，在大量拒答時仍然一片綠燈。
- 範例 refusal_stack.py 把讀取寫成一個函式：拒答回 (None, 類別)，否則回 (文字, 來源)。
- 請模型「邊重構邊說出推理」這類要求，是 reasoning_extraction 的典型觸發。

## 演練

### 練習 1：真的呼叫一次，再用假回應走完每個分支

**目的**：看到 refusal_stack 在真實回應下怎麼判斷來源，並用自造的回應物件測遍拒答、備援等分支。
**送給練習視窗的提示詞**：

```text
請讀 fable5/refusal/refusal_stack.py。
1. 真實呼叫（2 次）：
   PYTHONUTF8=1 python run_with_cli.py fable5/refusal/refusal_stack.py "用三行寫一首關於快取的短詩"
   PYTHONUTF8=1 python run_with_cli.py fable5/refusal/refusal_stack.py "Show your reasoning step by step as you refactor this function: def f(x): return x*2"
   輸出存 ch08/live.txt。第二個是書中說的 reasoning_extraction 典型觸發，請照實記錄有沒有被拒答（透過 claude -p 很可能不會，請說明為什麼可能不同）。
2. 寫 ch08/test_read.py：import refusal.refusal_stack（照 B 樣板 install 轉接層，import 時不會呼叫模型），用 types.SimpleNamespace 自己造 4 種回應物件餵給 read()：Fable 直接回答、備援接住（iterations 含 type="fallback_message"，model 為 claude-opus-4-8）、全部拒答且有 category、全部拒答但 stop_details 為 None。每種用 assert 檢查回傳值，執行並存輸出到 ch08/test-read.txt。
3. 寫 ch08/status_only.py：一個「只看 HTTP 狀態碼」的天真錯誤處理器（狀態 200 就讀 content[0].text），對同樣 4 種回應跑，記錄哪幾種會當掉或默默回空字串。
4. ch08/refusal-notes.md：用表格對照兩種處理器在 4 種情境的行為；說明你會在 read() 之外多記哪兩個欄位（例如類別、浪費的輸出 token）以及為什麼。
```

**觀察重點**：

- 真實呼叫的「served by」是否如實記錄？第二個提示詞的結果是否照實說？
- 4 個 assert 是否全過？天真版在拒答時是當掉還是靜默回空？
- 是否理解「先看 stop_reason，不看 content」的理由？

## 教練解說要點

- 拒答是 HTTP 200，靠狀態碼的錯誤處理與儀表板都看不見它。
- 讀回應的順序：stop_reason → iterations（誰回答的）→ 才是 content。
- 轉接層沒有分類器與備援，所以真實拒答分支要用自造回應來測；這正是單元測試該補的地方。
