# ch05｜Fable Scanner：讓每份提示詞保持 Fable 原生

## 這章在講什麼

- 作者先稽核了一個第三方的 Fable 5 工具，再決定不信任它、自己重寫一個乾淨的版本：fable_scanner，三個子指令。
- `scan`：靜態檢查 CLAUDE.md、技能檔、代理設定，找出官方 Fable 5 提示指南裡列為反模式的寫法（大寫強調、喊 YOU MUST、超長條列、要求逐步輸出思考、顯示剩餘 token、送 temperature、手動 thinking 預算、沒接備援）。
- `canary`：固定一組提示詞定期跑，和第一次的基準線比，拒答率或延遲漂移就警告。
- `monitor`：只讀本機的 API 回應紀錄，統計拒答類別、備援、各模型花費，不連網。
- 原則：舊鷹架要「機械化」清掉，不靠人眼一份一份看。

## 作者做過的實驗／例子

- 要求模型「一步步說出內部思考過程」會直接觸發 reasoning_extraction 拒答。
- 沿用舊模板送 temperature、top_p 或手動思考預算，API 直接回 400。
- 範例資料夾有一份壞提示詞、一份好提示詞、一份設定檔、一份拒答紀錄，掃描與監控都能直接示範。

## 演練

### 練習 1：掃描、讀懂規則、把壞提示詞修到乾淨

**目的**：理解每條規則在擋什麼，並親手把壞提示詞修到 0 個發現。不需要呼叫模型。
**送給練習視窗的提示詞**：

```text
請讀 fable5/fable_scanner/rules.py 與 scan.py。
1. cd fable5 後執行 PYTHONUTF8=1 python -m fable_scanner scan fable_scanner/examples --format json，輸出存 ch05/scan-examples.json。
2. ch05/rules-table.md：rules.py 裡每一條規則一列：代碼、類別、嚴重度、適用（prompt 或 config）、它在擋什麼毛病（用自己的話）、範例檔裡有沒有被觸發。
3. 把 fable_scanner/examples/bad_prompt.md 複製成 ch05/fixed_prompt.md 並修改，直到 cd fable5 && PYTHONUTF8=1 python -m fable_scanner scan ../ch05/fixed_prompt.md 回報 0 個發現；保留原本的任務（修好失敗的 build），不可整份刪光。把每一版掃描結果附在 ch05/fix-log.md。
4. 再掃兩個你身邊的真實檔案：../CLAUDE.md（練習視窗規則）與 skills/ 資料夾，結果也附在 fix-log.md，並說明有沒有誤判（規則抓到但其實沒問題的）。
```

**觀察重點**：

- 規則表的數量是否與 rules.py 一致？
- fixed_prompt.md 是否真的 0 個發現、而且任務意圖還在？
- 對真實檔案的發現，能否分辨真問題與誤判？

### 練習 2：真的跑一次金絲雀，再用監控分析自己的紀錄

**目的**：用轉接層讓 canary 真的打模型建立基準線，並把這次的呼叫紀錄交給 monitor 分析。
**送給練習視窗的提示詞**：

```text
請讀 fable5/fable_scanner/canary.py 與 monitor.py。canary 會在「目前工作目錄」寫 .fable-scanner/，所以請在 ch05/ 裡執行：
1. cd ch05 後執行 PYTHONUTF8=1 python ../run_with_cli.py -m fable_scanner canary init。
2. 打開 ch05/.fable-scanner/baseline.json，在 prompts 陣列加入一個你自己設計的提示詞（id 用 my-format，要求固定格式輸出，expect 至少用 contains 與 max_len 兩種檢查）。這樣總共 5 個提示詞。
3. 執行 K143_CLI_LOG=canary-calls.jsonl PYTHONUTF8=1 python ../run_with_cli.py -m fable_scanner canary run（5 次呼叫），輸出存 ch05/canary-run1.txt。
4. 回到 fable5 目錄執行 PYTHONUTF8=1 python -m fable_scanner monitor ../ch05/canary-calls.jsonl，輸出存 ch05/monitor.txt。
5. ch05/canary-notes.md：每個提示詞的分數與延遲；你設計的 expect 是否太鬆或太緊（拿實際輸出說明）；為什麼第一次 run 不會比較；monitor 的成本數字從哪個欄位算出來；說明轉接層下看不到拒答類別與備援的原因，以及真實部署時這兩個欄位為什麼最重要。
```

**觀察重點**：

- baseline.json 是否真的多了第 5 個提示詞並被執行？
- 對 expect 鬆緊的判斷是否拿實際輸出當證據？
- 有沒有說清楚第一次 run 只是快照？

## 教練解說要點

- 提示詞也要 lint：舊鷹架會在新模型上變成 400 或拒答，靠人眼不可靠。
- scan 管「寫法」、canary 管「行為漂移」、monitor 管「發生過什麼」，三者互補。
- 作者先稽核再自己重寫，是在示範：連提示詞工具也要先驗證才信任。
- 金絲雀的價值在第二次之後；第 17 章會真的做漂移比較。
