# ch07｜把生產機隊從 Opus 4.8 遷移過來

## 這章在講什麼

- 換模型不是改一個字串：舊請求裡的取樣參數（temperature、top_p、top_k）、手動 thinking 預算，在 Fable 5 會直接回 400。
- 從對話歷史帶過來的思考區塊，換模型之後不會報錯，但會被當成無效的輸入 token 計費。
- 遷移前要補上備援（fallbacks＋server-side fallback beta），因為拒答是 HTTP 200 加空內容，不接備援就卡死。
- effort 要明確寫出來，整個機隊要調整時才只要改一個地方。
- 作者的做法：先用 linter 掃每個請求本體，CI 遇到 error 就擋；再逐步切換流量並比對新舊輸出。

## 作者做過的實驗／例子

- 1M 上下文全部按標準費率計價，過去為了避開 20 萬 token 門檻而切分請求的邏輯可以拿掉。
- 把 Fable 的歷史重放給 Opus 時沒剝掉思考區塊：不報錯，但帳單多了一截。
- migration_linter 回傳 (欄位, 嚴重度, 訊息)，讓 CI 可以在任何 error 時讓建置失敗。

## 演練

### 練習 1：把舊請求修到可以上 Fable 5，並寫 CI 閘門

**目的**：用 linter 找出會 400 的欄位，修好之後用程式把關。不需要呼叫模型。
**送給練習視窗的提示詞**：

```text
請讀 fable5/migration/migration_linter.py、sample_opus_request.json 與 test_migration_linter.py。
1. cd fable5 後執行 PYTHONUTF8=1 python migration/migration_linter.py migration/sample_opus_request.json 與 PYTHONUTF8=1 python -m migration.test_migration_linter，輸出存 ch07/lint-before.txt。
2. 寫 ch07/fixed_request.json：從範例複製後修到 0 個 error、0 個 warn（model 改 claude-fable-5、移除取樣參數與手動 thinking、剝掉 assistant 的思考區塊、加 fallbacks 與 output_config.effort），再跑 linter，輸出存 ch07/lint-after.txt。
3. 在 ch07/requests/ 放 4 份請求本體：你修好的、原始範例、一份只有 top_k 的、一份 thinking 為 {"type":"disabled"} 的。寫 ch07/ci_gate.py：import migration.migration_linter 的 lint()，掃整個資料夾，任何 error 就印出檔名與欄位並以 exit code 1 結束。執行並把輸出與 exit code 存 ch07/ci-gate.txt。
4. ch07/migration-notes.md：每種 finding 會造成什麼後果（400、白花錢、卡死、日後難改），以及 linter 沒檢查、但你認為遷移時也該檢查的一件事。
```

**觀察重點**：

- fixed_request.json 是否真的 0 error 0 warn（有 lint-after.txt 為證）？
- ci_gate.py 的 exit code 是否正確反映結果？
- top_k 與 thinking disabled 是否被抓到？

### 練習 2：影子比對：同樣提示詞，新舊模型各跑一次

**目的**：體驗逐步切換前的「影子比對」：不比字串是否一樣，而是比可檢查的性質。
**送給練習視窗的提示詞**：

```text
寫 ch07/shadow_compare.py：照 B 樣板 install 轉接層，準備 2 個代表你機隊日常工作的提示詞（例如「把這段錯誤訊息分類成 bug／config／network，只回一個詞」與「用三點條列總結這段部署紀錄」，附上你自擬的短輸入），分別用 model="claude-opus-4-8" 與 model="claude-fable-5" 送出，output_config 用 {"effort":"medium"}。共 4 次呼叫。
每個提示詞定義 2～3 個性質檢查（例如：回答是否只有一個詞且在允許清單內、是否恰好三行條列、長度上限），對兩個模型的輸出各跑一次，並記錄 output_tokens。
結果存 ch07/shadow-results.md：表格列「提示詞／模型／性質通過數／output_tokens／原文前 80 字」；最後寫切換建議：這兩個工作可以切到 Fable 5 嗎？如果性質都通過但輸出字面不同，為什麼這不算回歸？並說明轉接層忽略 max_tokens 與 fallbacks 這件事對比對結果有什麼影響。
```

**觀察重點**：

- 是否用性質檢查而不是字串完全相等？
- output_tokens 是否來自真實回傳的 usage？
- 切換建議是否根據表格數據？

## 教練解說要點

- 遷移的第一步是 lint：會 400 的欄位、白花錢的思考區塊、沒接的備援，全部在 CI 擋下。
- 切換前先影子比對；比的是性質，不是字面。
- effort 寫明，未來全機隊調整只改一處。
