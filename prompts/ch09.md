# ch09｜備援切換時別付兩次錢

## 這章在講什麼

- 用 SDK 中介層或伺服器端備援時，平台會處理好計費；但若你自己寫重試（其他語言、裸 HTTP、自訂迴圈），在備援模型上重送會從頭寫一次提示快取，比讀快取貴。
- 平台在拒答時附一個一次性的 fallback_credit_token；重試時原樣帶回去，這次重試就按「一開始就在備援模型上」計價。
- 前提是請求本體要「完全一致」：只能換 model、加上 credit，其他欄位一個都不能動，連清洗訊息陣列都不行。
- 另一個辨識問題：黏性路由（sticky）時這一輪直接由備援服務，沒有原模型的那次嘗試，要和真正的備援分開統計。

## 作者做過的實驗／例子

- 自己捕捉拒答再重試、卻沒帶 token，等於付兩次昂貴的快取寫入。
- 重試前「順手」清掉訊息裡的空白區塊，平台判定本體不一致，折抵失效。
- 範例 credit_retry.py 只示範形狀，作者明說有中介層時不要自己寫。

## 演練

### 練習 1：用假 client 驗證「本體完全一致」

**目的**：轉接層沒有 credit 機制，所以用會記錄請求的假 client 來測重試邏輯，並親手示範「改了一個欄位就失效」。不需要呼叫模型。
**送給練習視窗的提示詞**：

```text
請讀 fable5/fallback_credit/credit_retry.py。
寫 ch09/test_credit.py（sys.path 加入 fable5，直接 import fallback_credit.credit_retry，這支沒有 import anthropic）：
1. 做一個 FakeClient：client.beta.messages.create(**kw) 會把每次的 kw 存進清單，並依你預先排好的劇本回傳 SimpleNamespace 回應（拒答時 stop_reason="refusal"，stop_details 帶 fallback_credit_token 與 fallback_has_prefill_claim）。
2. 測 4 個情境並用 assert 檢查：(a) 第一次就成功，只呼叫 1 次；(b) 拒答且有 token，第二次請求除了 model 與 fallback_credit 之外和第一次完全相同；(c) 拒答但沒有 token，仍然重試但沒帶 credit；(d) served_by_sticky：只有 fallback_message 沒有 message 為 True，兩者都有為 False。
3. 寫 body_matches(first, retry) 函式：忽略 model 與 fallback_credit 後比較兩個請求本體，並示範一個「好心清洗訊息」的錯誤重試（例如刪掉空字串的 content 區塊）會讓它回 False。
執行並把輸出存 ch09/test-credit.txt。最後寫 ch09/credit-notes.md：用一個你自擬的數字例子（例如 5 萬 token 的系統提示詞，寫快取 1.25 倍、讀快取 0.1 倍，價格用 README 的 Fable／Opus 單價，請標明是假設）算出有帶 token 與沒帶 token 的重試成本差，並說明轉接層為什麼無法示範真正的 credit。
```

**觀察重點**：

- 情境 (b) 的 assert 是否真的逐欄比較，而不是只比 model？
- body_matches 的反例是否合理、而且真的回 False？
- 成本例子有沒有標明假設、算式能不能重算？

## 教練解說要點

- 自己寫重試時，一次性 credit token 是避免重付快取寫入的關鍵。
- 「完全一致」是字面意思：只換 model、加 credit，其他都不准動。
- 黏性路由與真正的備援要分開統計，否則備援率會失真。
- 能用 SDK 中介層或伺服器端備援，就不要自己寫這段。
