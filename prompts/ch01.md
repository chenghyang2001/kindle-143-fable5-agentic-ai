# ch01｜改變了什麼：Fable 5、Mythos 5 與 Harness

## 這章在講什麼

- Fable 5 與 Mythos 5 是同一個能力等級的兩種部署：Fable 是一般可用、帶安全分類器的版本；Mythos 只開放給經核准的防禦性資安專案。兩者都是 1M 上下文、思考永遠開著。
- 作者的核心主張：工程重心已經從「把提示詞寫得很精巧」移到「圍繞模型的 Harness」——給目標、邊界、驗證方式與停止條件，模型自己補上做法。
- 舊世代的鷹架（大寫 IMPORTANT、YOU MUST、十幾條條列、逐步列出思考過程、顯示剩餘 token）在新模型上反而有害：有的會讓它提早收工，有的直接觸發拒答。
- 作者整理了「第一天就能用」的五個提示詞模組：邊界、接地進度、自主性、白話摘要、上下文平靜。每個模組各擋一種新模型特有的毛病。
- 本章的作業是第一個 Harness 專案：一個記憶資料夾、一份可重用的系統提示詞、一組驗證指令與驗證子代理規格、一頁執行評估。

## 作者做過的實驗／例子

- 價格是輸入每百萬 10 美元、輸出 50 美元，正好是上一代旗艦的兩倍；若組織設定零資料保留，請求會直接被 400 擋下。
- 思考區塊預設不顯示內容，串流介面會出現好幾秒的空白，常被誤以為當掉。
- 範例程式碼的 README 列了六條「已寫進程式」的 API 注意事項：不送 thinking 參數、用 effort 控深度、每個請求都接備援、先看 stop_reason 再讀內容、Mythos 另有範圍閘門、做的人不當審的人。

## 演練

> 說明：練習視窗工作目錄裡有 `fable5/`（書附範例）與轉接層 `claude_cli_client.py`。要呼叫模型時都透過轉接層走 `claude -p`，不用 API 金鑰。用法見 practice/CLAUDE.md。

### 練習 1：用五個模組改寫舊提示詞，並讓模型真的回答一次

**目的**：親眼看到舊鷹架與 Harness 式提示詞的差別，不只是靜態比較，而是實際送給模型看行為。
**送給練習視窗的提示詞**：

```text
請先讀 fable5/fable_scanner/examples/bad_prompt.md 與 fable5/fable_scanner/examples/good_prompt.md，再讀 fable5/README.md 最後一節的 API 注意事項。
1. 寫 ch01/system_prompt.md：把 bad_prompt.md 改寫成一份 Harness 式系統提示詞（英文或中文都可），必須含五個小節：邊界（只評估不動手，除非明確授權）、接地進度（每個進度宣稱要對應工具結果）、自主性（小決定自己做、不停下來問、說要測就真的測）、白話摘要（最終報告用完整句子、不自創縮寫）、上下文平靜（不提剩餘 token、不為省空間刪工作）。每小節 1～3 句即可。
2. 掃描前後對照：cd fable5 後分別執行 PYTHONUTF8=1 python -m fable_scanner scan fable_scanner/examples/bad_prompt.md 與 PYTHONUTF8=1 python -m fable_scanner scan ../ch01/system_prompt.md，把兩份輸出存進 ch01/scan-compare.md，並用表格說明每個被抓到的規則代碼在你的新版怎麼消失。
3. 真的送一次：寫 ch01/try_prompt.py（照 practice/CLAUDE.md 的 B 樣板 install 轉接層），用 claude_cli_client.Anthropic().messages.create 送同一個任務「CI 的 build 失敗了，錯誤是 ModuleNotFoundError: No module named 'yaml'，請處理。」兩次：一次 system 用 bad_prompt.md 全文，一次用你的 system_prompt.md，model 用 claude-fable-5。共 2 次呼叫。兩份回答存成 ch01/answer-old.md、ch01/answer-new.md。
4. ch01/compare.md：比較兩份回答——哪一份直接宣稱改了檔案或「已修好」、哪一份先評估再提出建議、哪一份有自創縮寫或冗長逐步敘述。只寫你在回答中真的看到的，沒看到就寫「沒有出現」。
```

**觀察重點**：

- 新版掃描是否 0 個 error？被抓到的規則代碼有沒有逐一對上原因？
- 兩次真實回答的差異是否真的來自提示詞（例如新版只給建議、沒有宣稱已動手），還是兩份其實差不多？差不多也要照實說。
- 有沒有超過 2 次模型呼叫？

### 練習 2：搭起第一個 Harness 專案骨架

**目的**：把本章作業縮小成可在幾分鐘內完成的版本，體會「記憶＋系統提示詞＋驗證＋評估」四件套。
**送給練習視窗的提示詞**：

```text
請讀 fable5/templates/memory-scaffold.md 與 fable5/templates/nightly-verifier-loop.md，然後替一個虛構任務「每晚讓 fable5/fable_scanner 的測試保持全綠」搭 Harness 骨架，全部存在 ch01/harness/：
1. memory/INDEX.md 與 memory/lessons/ 底下 3 個 lesson 檔（一課一檔），內容取材自本章：例如「不要顯示剩餘 token」「不要送 temperature」「先看 stop_reason」。每個檔第一行是摘要、接著細節、最後一行是出處行（provenance：哪個檔案、哪一行或哪個指令輸出讓你學到這件事）。
2. SYSTEM.md：可重用的系統提示詞，引用 ch01/system_prompt.md 的五個模組，再加上這個任務的目標與原因（為什麼要每晚全綠）。
3. VERIFY.md：驗證指令（實際可跑的那一行：cd fable5 && PYTHONUTF8=1 python -m fable_scanner.test_scanner）與一份驗證子代理規格（它只看指令輸出、不看執行者的敘述，回 PASS/FAIL）。
4. 真的跑一次驗證指令，把輸出貼進 EVAL.md，並在 EVAL.md 用一頁寫：這次執行的結果、哪幾個模組被用上、還缺什麼。
5. 最後執行 cd fable5 && PYTHONUTF8=1 python -m fable_scanner scan ../ch01/harness，把結果附在 EVAL.md 末尾。
```

**觀察重點**：

- lesson 檔是否都有可追溯的出處行，而不是空泛的「本章提到」？
- EVAL.md 的測試結果是不是真的跑出來的（能看到 ok／all checks passed 字樣）？
- 掃描器有沒有在自己寫的 Harness 檔案裡抓到舊鷹架？

## 教練解說要點

- 新模型最大的改變不是更聰明，而是「舊的哄法變成毛病」；Harness 取代了精巧提示詞。
- 五個模組各擋一種毛病：亂動手、假進度、停下來問、看不懂的縮寫、被 token 數嚇到。
- 練習 1 是同一任務、兩份提示詞的真實對照；若差異不明顯，也是一種發現：模型本身已經不太需要哄。
- 第一個 Harness 不必大：記憶、提示詞、驗證、評估各一份，下一章再讓它變成迴圈。
